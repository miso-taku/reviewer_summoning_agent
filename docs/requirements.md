# 要求定義書 — レビュアー召喚 Web

| 項目 | 内容 |
|------|------|
| 文書ID | REQ-2026-001 |
| 版 | 1.0 |
| 対象 | 技術ブログ／LT 向け「レビュアー召喚」ローカル Web アプリ |
| 前提スタック | Next.js（App Router）+ Tailwind、FastAPI + PydanticAI、同一マシン上の 2 プロセス |

---

## 1. 目的・背景

### 1.1 目的

執筆者が**テーマ**と**レビュー対象テキスト**（原稿・構成メモ・スライド要約など）を入力すると、LLM を用いて**重複の少ない 3 視点のレビュアー**を生成し、同一原稿に対する**並列レビュー**を経たうえで、**編集長エージェント**が**統合コメント**（全体方針・優先修正・重複整理）を出力する。利用シーンは技術ブログ執筆や LT 原稿の推敲支援とする。

### 1.2 成功の定義（受入の目安）

- ローカル環境でフロントと API を起動し、1 回の操作で「3 名の構造化レビュー」と「編集長の統合結果」が画面で確認できる。
- API キーはバックエンドのみに保持し、ブラウザからは露出しない。
- 主要な失敗（入力不備、LLM 失敗、タイムアウト）がユーザーに分かる形で返る。

## 4. ユースケース

### 4.1 ユースケース一覧

| UC-ID | 名称 | 主アクター | 説明 |
|-------|------|------------|------|
| UC-01 | レビュー依頼を実行する | 執筆者 | テーマと対象テキストを入力し、パイプラインを実行して結果を得る |
| UC-02 | 進行状況を把握する | 執筆者 | 召喚・各レビュー・編集長の段階が UI で分かる |
| UC-03 | 失敗時に原因を把握する | 執筆者 | 入力エラー、サーバエラー、LLM エラー等を区別して表示 |

### 4.2 UC-01 主シナリオ（要約）

1. ユーザーがテーマとレビュー対象テキスト（原稿・構成メモ・スライド要約のいずれかまたは併記）を入力する。
2. ユーザーが送信する。
3. システムが召喚により 3 名のレビュアーを生成する。
4. システムが 3 名のレビューを並列実行する。
5. システムが編集長により統合結果を生成する。
6. ユーザーが 3 名の出力と編集長の統合を画面で確認する。

**代替・例外**：入力制約違反、ネットワーク／LLM エラー、タイムアウトは UC-03 に連動して扱う（詳細は機能設計書）。

## 6. 機能要求（詳細）

### 6.1 パイプライン（ビジネスルール）

1. **召喚**：入力テーマと対象テキストから、重複の少ない 3 視点のレビュアー（表示名・専門軸・観点）を構造化生成する。
2. **三連レビュー**：各ペルソナが**同一原稿（および関連メモ）**を対象に、**並列**でレビューする。出力スキーマは Pydantic 等で固定する（具体フィールドは機能設計書）。
3. **編集長**：原稿・テーマ・3 名の構造化レビューを入力に、統合コメント・優先修正・指摘のマージ／矛盾の解消を行う。プロンプトには**幻覚抑制**の指示を含める。

### 6.2 UI（最小）

- 送信中の**段階表示**。
- **編集長ブロックの強調表示**（レイアウト詳細は機能設計書のワイヤで固定）。

## 7. 入力制約

| 入力項目 | 必須 | 制約・備考 |
|----------|------|------------|
| テーマ | 必須 | 最大文字数・空文字禁止は機能設計で数値化 |
| 原稿本文 | 条件付き | 「レビュー対象テキスト」として原稿・構成メモ・スライド要約のいずれか以上を必須とするかは機能設計で確定。本書では**少なくとも 1 つの非空テキストブロック**を必須とする |
| 構成メモ | 任意 | 長文時はトークン／レイテンシ影響あり（非機能参照） |
| スライド要約 | 任意 | 同上 |

**ファイルアップロード**：初版はスコープ外とし、テキスト貼り付けのみを想定する（必要なら将来 UC として追加）。

## 8. 非機能要求

### 8.1 品質・可用性

| ID | 内容 |
|----|------|
| REQ-NF-010 | 主要フロー（UC-01）がローカルで安定して完走できること |
| REQ-NF-011 | ドメイン・アプリケーション層は外部 I/O なしで単体テスト可能な設計（DDD・TDD 方針） |
| REQ-NF-012 | LLM 往復回数が多いため、**タイムアウト**と**ユーザー向けエラーメッセージ**を定義する（閾値は機能／技術設計） |

### 8.2 セキュリティ・プライバシー

| ID | 内容 |
|----|------|
| REQ-NF-020 | LLM API キーはサーバ環境変数等にのみ保持し、フロント・リポジトリにコミットしない |
| REQ-NF-021 | CORS は開発用にローカル Next のオリジンのみ許可（本番展開時は再設計） |
| REQ-NF-022 | 原稿はサーバ上で必要最小限の期間のみメモリ保持し、永続化しない（初版） |

### 8.3 性能・コスト（目標レベル）

| ID | 内容 |
|----|------|
| REQ-NF-030 | 長文原稿はレイテンシ・コストが増大するため、上限または分割方針を技術設計で定義する |
| REQ-NF-031 | 3 レビューは並列実行とし、逐次実行より待ち時間を短縮する |

### 8.4 運用・互換性

| ID | 内容 |
|----|------|
| REQ-NF-040 | Python／Node の推奨バージョンは技術設計書またはルート README に記載 |

## 10. 用語集

| 用語 | 定義 |
|------|------|
| 召喚 | テーマと対象テキストから 3 名のレビュアーペルソナを生成するステップ |
| 三連レビュー | 生成された 3 名が同一原稿を並列にレビューするステップ |
| 編集長 | 3 名の出力を統合し、全体方針・優先修正・重複整理等を行うエージェント |
| レビュー対象テキスト | 原稿本文、構成メモ、スライド要約など、ユーザーが貼り付けるテキストの総称 |
| 統合コメント | 編集長が出力する、全体向けのまとめコメントおよび優先度付き指摘の集合（具体スキーマは機能設計） |
