## 1. 目的・範囲

### 1.1 目的

本書は、**テストレベル**（単体・結合・E2E）の役割分担、**優先度**、**カバレッジ方針**、**モック／スタブ方針**、**完了基準**を固定し、実装フェーズの TDD・CI と矛盾しないようにする。

### 1.2 スコープ

| 対象 | 本書での位置づけ |
|------|------------------|
| `backend/` の `domain` / `application` / `presentation` | 単体・API 結合の主対象 |
| `backend/` の `infrastructure`（PydanticAI・実 LLM） | スタブ／フェイクで置換した結合テストが主。実 LLM は **CI 既定では実行しない** |
| `web/`（Next.js） | クライアント検証・状態遷移・表示の単体（推奨）および必要最小限の E2E（任意） |
| 本番デプロイ・負荷・セキュリティ監査 | 初版スコープ外（要求書のローカル第一義に整合） |

### 1.3 スコープ外

- CI での **LLM 実呼び出し必須化**（要求 REQ スコープ外。本書でも既定 CI から除外）
- モバイル実機網羅、多言語 UI の回帰マトリクス全体

## 3. テストレベル定義

### 3.1 単体テスト（Unit）

**定義**: 1 モジュールまたは少数の純粋関数・クラスを、**外部ネットワーク・実 LLM・実 DB なし**で実行するテスト。

| 置き場（鏡像） | 主対象 | 使用ツール |
|----------------|--------|------------|
| `tests/domain/` | 値オブジェクト（`Theme`、`ManuscriptBundle` 等）、集約 `ReviewSession` の不変条件、ドメイン例外 | pytest |
| `tests/application/` | `RunReviewPipelineUseCase`：**フェイクポート**（固定戻り値）で召喚→並列レビュー→編集長の順序と失敗時の正規化 | pytest、pytest-asyncio |
| `tests/presentation/` | 例外→HTTP ステータス・`error.code` のマッピング、スキーマのエッジケース（可能ならルータをモック DI で薄く） | pytest、FastAPI `TestClient`（**LLM は呼ばない**） |

### 3.2 結合テスト（Integration）

**定義**: アプリケーション境界をまたぎ、**HTTP または非同期パイプライン全体**を検証する。LLM は **スタブ／フェイク実装**（固定 JSON または録画レスポンス）に置き換える。

| ID | 内容 | ツール |
|----|------|--------|
| IT-API-01 | `POST /api/v1/review`：依存注入で `infrastructure` をスタブに差し替え、200 ボディと OpenAPI 相当スキーマ整合 | httpx `AsyncClient` + FastAPI アプリ、`pytest-asyncio` |
| IT-API-02 | 入力検証：422 + `VALIDATION_ERROR`、詳細 `details` の有無 | 同上 |
| IT-API-03 | タイムアウト：スタブが遅延返答 → 504 + `REQUEST_TIMEOUT`（TEC §7.3 に合わせて期待値を固定） | 同上 |
| IT-API-04 | LLM エラー系：スタブが例外 → 502／503 と `error.code` のマッピング | 同上 |

**境界**: 結合テストでは **PydanticAI を実装したクラスを経由してもよい**が、その背後の HTTP は **respx** 等でモックするか、ポートの **InMemoryFake** を `infrastructure` の手前まで含めた「狭い結合」に留める。チーム内でどちらを「IT-API」と呼ぶかは README に一文で統一する。

### 3.3 E2E テスト（End-to-End）

**定義**: ブラウザ（またはブラウザ自動化）からフロント経由で API を呼び、ユーザー視点の UC-01 を検証する。

| 方針 | 内容 |
|------|------|
| 初版 | **任意**。工数が許す場合のみ Playwright（または Cypress）で「ローカル Next + スタブ API」または「Next + 実 API（スタブ LLM）」のいずれかを 1 本以上 |
| API スタブ | E2E 専用のモックサーバ、または環境変数でバックエンドをフェイクモード起動する方式のいずれかを README に記載 |
| 優先シナリオ | UC-01 主シナリオ（入力→送信→3 カード＋編集長ブロック表示）。UC-03 は代表的な 422 を 1 件 |

**LLM 実呼び出しを伴う E2E**は、手動受入または `@pytest.mark.llm_live` 等の **非 CI** 実行とする（§6.2）。

## 4. テスト対象一覧（レイヤ別）

### 4.1 ドメイン層（必須・TDD 第 1 波）

- `Theme`：トリム、1〜2000 文字、空不可
- `ManuscriptBundle`（または同等 VO）：3 ブロックの少なくとも 1 つ非空、合計 200000 文字以下
- `ReviewSession`：レビュアー 3 名確定前の並列レビュー禁止、レビューと `reviewer_id` の整合、編集長は 3 レビュー後のみ、など TEC §4.4.1 の不変条件
- ドメイン例外型（入力検証 vs 想定外）の区別

### 4.2 アプリケーション層（必須・TDD 第 2 波）

- `RunReviewPipelineUseCase.execute`：
  - 召喚 → `asyncio.gather` 相当の並列 3 レビュー → 編集長の **呼び出し順・回数**（ポートの呼び出しログで検証可能にする）
  - いずれかのレビュー失敗時のキャンセル／例外収集方針（TEC §6.2 の採用案に合わせた期待値）
- ポート **インターフェース**に対するフェイク実装のみを注入（PydanticAI に依存しない）

### 4.3 プレゼンテーション層

- リクエスト JSON → ユースケースへのマッピング
- ユースケース結果 → `ReviewSuccessResponse`
- ドメイン／アプリケーション例外 → FUN §8.2 の HTTP + `ErrorEnvelope`

### 4.4 インフラストラクチャ層

- **単体**: Pydantic モデルとプロバイダレスポンスのパース変換のみに限定する小テスト（任意）
- **実 LLM**: §6.2 のマーク付きのみ。CI ではスキップ

### 4.5 フロントエンド（`web/`）

| 種別 | 内容 |
|------|------|
| 単体（推奨） | `lib/validation.ts`：FUN §5.1 の定数・必須組合せ・合計サイズのクライアント検証 |
| コンポーネント（推奨） | 段階インジケータ、`Idle`/`Loading`/`Result`/`Error` の表示切替（React Testing Library 等） |
| E2E（任意） | §3.3 |

## 5. カバレッジ方針

### 5.1 コードカバレッジ（計測ツール）

| 対象 | ツール（案） | 目標（初版） |
|------|----------------|--------------|
| バックエンド Python | `pytest-cov` | **domain + application の行カバレッジ 85% 以上**を目安（厳密ゲートはチーム合意で調整可） |
| presentation | 同上 | 分岐の多い例外マッピングを優先。数値目標は 70% 前後を目安 |
| infrastructure（PydanticAI） | 同上 | スタブ経由の経路を優先。実装が薄ければ低くても可 |
| フロント TypeScript | Vitest + `@vitest/coverage-v8`（採用時） | `validation.ts` を **90% 近辺**。UI は重要パス優先 |

**注**: カバレッジは **品質の十分条件ではない**。不変条件・エラーコードの表（§8）を満たすことを優先する。

### 5.2 要求カバレッジ（トレース）

- REQ-F-001〜006 および UC-01〜03 は、[§8 テストケース／回帰マトリクス](#8-テストケース回帰マトリクス抜粋) に **対応テスト ID** を付与して追跡する（実装時に `pytest` の `@pytest.mark.req("REQ-F-001")` 等でも可）。

## 6. モック・スタブ・フェイク方針

### 6.1 用語

| 用語 | 本プロジェクトでの使い方 |
|------|--------------------------|
| **フェイク** | `ReviewerSummoningPort` 等の **同一シグニチャ**で、メモリ内の固定データを返す実装（application 単体で使用） |
| **スタブ** | 結合テストで LLM HTTP を `respx` 等で短絡し、固定 JSON を返す |
| **スパイ** | 呼び出し順・回数の検証が必要な場合に限り使用（乱用しない） |

### 6.2 LLM 実呼び出し

| 実行環境 | 方針 |
|----------|------|
| 既定 CI（PR／main） | **実行しない**。`-m "not llm_live"` または `LLM_LIVE=0` でスキップ |
| ローカル開発 | 開発者任意。`.env` にキーがある場合のみ `@pytest.mark.llm_live` または手動スクリプト |
| 夜間／手動パイプライン | 任意で `llm_live` を有効化しスモーク（コスト・安定性に注意） |

### 6.3 フロントの API 呼び出し

- 単体テスト：`fetch` を `msw` または vi.mock でスタブ
- E2E：§3.3 に従いバックエンドをスタブモードで起動するか、API モックを立てる

### 6.4 時刻・UUID

- **決定性**: `meta.completed_at` や `request_id` はテストで `freezegun`／固定 UUID ジェネレータを注入できるよう、生成をポートまたはコンストラクタ引数で差し替え可能にする（設計レビュー項目）。

## 7. 優先度（リスクベース）

| 優先度 | 内容 | 例 |
|--------|------|-----|
| P0 | 課金・セキュリティに直結、または UC-01 主シナリオが成立する最低限 | 入力検証、200 正常系（スタブ）、API キーがフロントに出ないことの静的確認（grep／lint 任意） |
| P1 | 失敗時のユーザー体験・運用で頻発 | 422／502／503／504、タイムアウト、並列レビュー 1 本失敗時の挙動 |
| P2 | 回帰コストが高いが発生頻度は中 | `priority_fixes` 上限、配列トリム |
| P3 | 境界値の網羅、UI アニメーションの細部 | 文字数ちょうど境界、インジケータの経過時間演出のみの変更 |

**リグレッション**: 不具合修正ごとに **再発防止テスト** を P0/P1 に追加する。

## 9. 完了基準（ゲート）

初版リリース（ローカル完走の受入）を満たすために、以下を **すべて**満たすこと。

1. **P0 の自動テスト**が CI でグリーン（LLM 実呼び出しなし）。
2. `domain` および `application` の主要不変条件・ユースケースが単体テストで表現されている（§4.1〜4.2）。
3. `POST /api/v1/review` の **結合テスト**（IT-API-01 に相当）が少なくとも 1 本存在し、スタブ LLM で 200 を検証する。
4. 機能設計 §8.2 に列挙された `error.code` のうち、実装したコードについて **HTTP ステータスとボディ**がテストで固定されている。
5. README に **テスト実行コマンド**（例: `pytest`、`pytest -m "not llm_live"`、`pnpm test`）が記載されている。

**手動受入（推奨）**: ローカルで実キーを用いた 1 回完走（計画書の成功定義）。記録はリリースノートまたはチェックリストに任意で残す。

## 10. テストデータ・フィクスチャ

| 種類 | 方針 |
|------|------|
| 最小有効リクエスト | `theme` 短文字列 + `draft_body` のみ非空 |
| 境界値 | テーマ 2000 文字ちょうど、合計 200000 文字ちょうど（生成スクリプトまたは圧縮フィクスチャ） |
| 異常 JSON | 型不一致、余分フィールド（許容／拒否は OpenAPI 方針に合わせて 1 テストで固定） |

**個人情報・実原稿**: リポジトリに含めない。サンプルは架空文で生成する。

## 11. 非機能・運用

| 項目 | テストでの扱い |
|------|----------------|
| 実行時間 | 既定 CI は **合計 10 分以内**を目安。遅い結合は並列 `pytest -n auto` を検討 |
